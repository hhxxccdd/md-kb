# MD-KB 项目架构说明与面试设计取舍

> 本文以当前代码为准，重点说明文档编辑、多人协同与 AI 协同写作三个核心场景。它既是重构后的复盘材料，也可作为面试前的项目表达提纲。

## 1. 项目要解决什么问题

MD-KB 是一个 Markdown 知识库项目，核心不是“能编辑一篇文章”，而是让用户能安全地完成下面三件事：

1. 创建、编辑、搜索和管理 Markdown 文档；
2. 多人同时编辑同一篇文档；
3. 在不让 AI 自动篡改协作文档的前提下，获得润色和多语言翻译建议。

项目的设计原则是：**真实文档只有用户确认后才能变化；AI 生成内容在确认前只是当前用户私有的候选稿。**

这条原则决定了后续的状态归属、Yjs 同步边界，以及 AI 差异预览的实现方式。

## 2. 当前前端目录与职责边界

前端采用“按业务 feature 组织，通用能力保留在共享目录”的混合方式。

```text
frontend/src/
├── views/                         # 路由页面，负责页面级编排
│   ├── EditorPage.vue
│   ├── adminPage.vue
│   ├── InvitePage.vue
│   └── Login.vue
├── features/
│   ├── ai/                        # AI 业务域
│   │   ├── api/streamAIRequest.ts
│   │   ├── components/
│   │   ├── composables/
│   │   ├── config/aiFeatures.ts
│   │   └── types/ai.ts
│   └── documents/                 # 文档列表、搜索等业务域
├── component/editor/              # 与具体编辑器 UI 强绑定的通用组件
├── composables/                   # 跨业务可复用的文档/协同能力
├── api/                           # 常规 HTTP API
├── stores/                        # 全局状态，例如登录用户
├── type/                          # 跨 feature 的领域类型
└── utils/                         # 无业务状态的工具函数
```

### 2.1 为什么不是把所有文件都移动到 feature 里

不是所有文件都属于某个业务域。

- `EditorPage.vue` 是页面装配层：路由、文档生命周期、协同、AI 功能在这里组合；它不应自己实现底层请求或 CodeMirror 扩展。
- `MyMdEditor.vue` 是对 `md-editor-v3` 的适配层，向外暴露受控的方法，例如 `getEditorView`、`replaceRange`；它不关心 AI 请求。
- `useDocumentCollaboration`、`useDocumentDraft` 处理的是文档生命周期能力，不属于 AI 功能。
- `features/ai` 内的组件和 composable 可以整体迁移、测试或扩展，而不会散落在 `views`、`utils`、`type` 中。

这是一种常见的工程折中：**按业务内聚，按技术共享**。目录不是目的，依赖方向清晰才是目的。

## 3. 编辑文档的生命周期

文档编辑不是单一的“保存中/已保存”，而是两个相互关联的状态机。

### 3.1 文档生命周期

```text
draft
  │ 用户首次输入
  ▼
creating
  │ 创建接口成功，路由变为 /edit/:id
  ▼
initializing-collab
  │ 编辑器、文档数据、Yjs 资源均准备完成
  ▼
collaborating
  │ 协同编辑与服务端持久化正常工作
  └── 失败 → create-failed
```

新建文档的关键点是：后端异步返回 `id` 前，用户仍然可能继续输入。因此创建阶段不能把“是否已有 id”当成唯一判断条件，而应由 `useDocumentDraft` 统一管理创建防抖、创建中状态、路由切换和销毁。

### 3.2 保存状态

```text
本地内容变化
  ├─ 草稿模式：防抖发送 createDocument / updateDocument
  └─ 协同模式：CodeMirror → Yjs update → WebSocket → 服务端持久化

请求或服务端确认成功 → 页面显示“已保存”
```

因此“已保存”不应只表示某个按钮点击完成，而应对应当前编辑模式的真实持久化确认。

## 4. 多人协同的数据流

```text
本地用户输入
  ↓
CodeMirror EditorView
  ↓ y-codemirror.next 绑定
Y.Text / Y.Doc
  ↓ WebSocket
协同服务端房间中的 Y.Doc
  ↓
其他用户的 Y.Doc
  ↓
其他用户的 CodeMirror
```

Yjs 解决的是并发文本操作的合并，不是“后写覆盖先写”。用户 A、B 同时编辑同一位置时，双方产生的 update 可以无中心锁地合并，最终收敛到一致状态。

`useDocumentCollaboration` 统一持有连接、在线用户、重连、资源销毁等逻辑；页面卸载或路由文档 id 切换时必须调用 `dispose`，避免旧 WebSocket 和旧 Y.Doc 继续占用资源。

## 5. AI 协同写作架构

### 5.1 功能定位

当前 AI 功能不是“文档问答机器人”，也不引入 RAG。它聚焦一个更贴近编辑器的场景：用户选中一段内容后，主动请求润色或指定语言翻译；系统展示建议，但永远由用户决定是否写入正文。

这种选择的原因：

- RAG 需要文档切分、索引、向量库、召回评估和权限过滤；对当前单个协作文档的润色/翻译场景投入产出不高。
- 泛问答在项目中容易沦为普通聊天框，和 Markdown 协作主链路结合较弱。
- “候选稿 + 差异审阅 + 用户确认”能直接体现协同写作中的安全边界与产品思考。

### 5.2 AI 模块拆分

```text
AiInlineHint
  └─ 用户选中足够长文本后，显示润色/翻译入口

AiLanguageMenu
  └─ 翻译前明确选择目标语言

useAIReview
  └─ 冻结本次会话的 inputText、expectedText、from/to、位置、动作和目标语言

useAIAction
  └─ 管理流式请求状态、结果、错误、AbortController 与旧请求隔离

streamAIRequest
  └─ 基于 fetch 读取 SSE，解析为统一的 token/done/error 事件

useAIInlineDiff
  └─ 用 CodeMirror Decoration 渲染候选稿，不修改真实 doc

AiReviewPopover
  └─ 只提供采纳、忽略、重试等操作，不承载大段结果内容
```

组件负责视图，composable 负责状态与副作用，页面负责组合与真实写入。这种拆分避免一个“AI 弹窗组件”同时承担请求、流解析、状态、编辑器写入和 UI 展示。

### 5.3 AI 请求与 SSE 流程

```text
用户点击润色/翻译
  ↓
useAIReview 冻结选区快照
  ↓
useAIAction 创建 AbortController
  ↓
streamAIRequest 使用 fetch 发起 POST + SSE 请求
  ↓
服务端逐段返回 SSE data
  ↓
token 逐步累加到 result
  ↓
useAIInlineDiff 根据最新 result 更新 Decoration
```

选择 SSE 而不是 WebSocket 的原因：这里是单向的“服务端持续推送生成文本”，HTTP 请求发起后服务端只需向客户端流式输出；SSE 的语义更简单，也更便于通过 `fetch` 和 `ReadableStream` 精确控制取消。WebSocket 已经用于双向协同编辑，不应为了 AI 单向流再增加一套双向协议。

SSE 解析不能假设一次 `reader.read()` 就是一条完整事件。网络分块可能把 JSON 截断，因此前端使用 `buffer` 累积内容，以空行分割完整 SSE 事件，再解析 `data:` 行。

### 5.4 取消、重试与旧请求保护

`useAIAction` 中维护当前的 `AbortController`。

- 新 AI 请求开始时取消旧请求；
- 点击忽略、页面卸载时取消当前请求；
- 通过“当前 controller 是否仍相同”判断晚到的结果或异常，旧请求不能覆盖新请求状态；
- 网络错误可重试，用户取消不提示为服务错误。

这解决了一个常见竞态：用户先点润色，又立即选中另一段内容点翻译；第一个请求晚返回时，不能覆盖第二次生成结果。

## 6. 为什么 AI 候选稿不直接进入 Yjs

这是本项目最重要的设计取舍。

### 错误方案

```text
AI 每收到一个 token
  → 直接写入 CodeMirror
  → 产生 Yjs update
  → 广播给所有协作者
```

问题是：未审核内容会污染共享文档；用户取消时还要回滚；流式多次写入会制造大量协同 update；其他人无法分辨哪些内容仍是建议。

### 当前方案

```text
AI token
  → 当前浏览器中的 review/result 状态
  → CodeMirror Decoration 临时视觉层
  → 用户点击“采纳”
  → replaceRange 一次性修改真实文档
  → Yjs 才同步最终变更
```

`Decoration` 不修改 `EditorView.state.doc`，所以它不触发 Yjs 同步。候选稿是当前用户的私有 UI 状态，只有最终确认的文本才是协作状态。

## 7. 内联差异预览与安全采纳

### 7.1 为什么使用 CodeMirror Decoration

候选稿需要“看起来在原文上”，但不能真的写进原文。`useAIInlineDiff` 使用：

- `StateField` 保存 Decoration 状态；
- `StateEffect` 命令式更新或清除 Decoration；
- `Decoration.mark` 标记待替换原文；
- `Decoration.widget` 以块级方式展示保留 Markdown 换行的候选稿；
- `EditorView.baseTheme` 将删除内容和新增内容分别染色。

这使 UI 可以展示类似 Git diff 的删除/新增效果，而 Markdown 源码和 Yjs 文档保持不变。

### 7.2 为什么保存 from/to 和原文快照

AI 请求耗时期间，编辑器当前选区可能因为失焦、用户点击按钮或协作者修改而改变。因此不能在采纳时依赖“当前选区”。

`AIReviewSession` 保存：

```ts
{
  inputText,
  expectedText,
  from,
  to,
  position,
  action,
  targetLanguage,
}
```

采纳时调用 `replaceRange(from, to, expectedText, replacement)`，并检查：

1. `from/to` 是否仍在当前文档范围内；
2. 该范围的真实文本是否仍等于 `expectedText`。

任何一项不满足都拒绝写入，要求用户重新生成建议。

### 7.3 为什么内容变化就让候选稿失效

当本地输入或远端 Yjs update 导致 `transaction.docChanged` 时，候选稿可能不再对应原来的语义位置。当前策略是保守地清除 Decoration 和 review 状态。

这会牺牲一点便利性，但换来协同编辑中更可靠的正确性。以后若要优化体验，可以把候选范围随 transaction 映射；但仍必须在替换前校验原文。

## 8. Markdown 格式保留的排障案例

曾出现 AI 候选稿把标题、列表、空行挤成一行的问题。排查后原因在服务端的输入处理：

```ts
// 错误：删除了 Markdown 的换行语义
content.replace(/[\r\n]/g, ' ').trim()
```

这不是有效的 Prompt 注入防护，反而在请求模型前破坏了 Markdown。

当前改为只统一换行符、移除空字符：

```ts
content
  .replace(/\r\n?/g, '\n')
  .replace(/\u0000/g, '')
```

并在 CodeMirror 中用块级 widget 和 `pre` 保留候选稿的换行。这个案例说明：内容格式是领域数据，清洗数据前必须理解其语义，不能为了“安全”粗暴删除换行。

### 8.1 AI 智能粘贴为什么不稳定

智能粘贴初版采用了最直接的链路：读取剪贴板纯文本，将其交给模型生成 Markdown，再通过现有候选稿机制预览和采纳。实际体验中，同一类输入有时会转换成标题、列表或表格，有时只返回普通段落；润色结果也存在风格和改写幅度波动。

这不是单一 Prompt 问题，而是三个不同层次的问题叠加：

| 问题层次 | 典型表现 | 对应方案 |
| --- | --- | --- |
| 输入信息丢失 | 网页标题和列表经 `readText()` 后只剩普通文本 | 优先读取 `text/html`，先做确定性 HTML → Markdown 转换 |
| 模型生成不确定 | 相同输入可能被表示为标题、加粗或普通段落 | 降低采样随机性，使用结构化输出、校验、有限重试和降级 |
| 缺少文档上下文 | 输出自身合法，但标题级别和当前文档不匹配 | 提取标题大纲、当前标题路径和光标附近文本作为上下文 |

因此，“输出是否稳定”和“输出是否适合插入当前位置”是两个独立目标。结构化输出可以保证模型返回的数据形状，却不能保证一个合法的一级标题适合放在当前三级章节下。上下文解决的是适配性，确定性转换和校验解决的是可靠性，两者不能互相替代。

### 8.2 目标架构：概率组件外包确定性系统

智能粘贴不应让模型独自负责从输入到最终 Markdown 的全部过程。目标链路是：

```text
读取 Clipboard
  ↓
HTML / Plain Text 分流
  ├─ HTML → 确定性 HTML-to-Markdown
  └─ Plain Text → LLM 识别语义结构
  ↓
提取当前文档上下文
  ↓
结构化 Block → 程序渲染 Markdown
  ↓
格式校验 + 内容保留校验 + 上下文适配校验
  ↓
失败时修复一次，仍失败则降级为基础 Markdown 或纯文本
  ↓
Decoration 预览
  ↓
用户采纳后通过一次 transaction 写入文档
```

这里的设计原则是：**模型负责理解含义，程序负责生成确定格式；AI 输出始终处于不可信候选态，通过校验和用户确认后才能进入真实文档。** 这与现有 `Decoration → accept → replaceRange` 的安全边界一致。

### 8.3 上下文不等于发送整篇文档

第一版无需把全文正文发送给模型。更合适的是提供小而有用的结构快照：

```ts
interface SmartPasteContext {
  documentTitle: string
  outline: Array<{ level: number; text: string }>
  headingPath: Array<{ level: number; text: string }>
  beforeText: string
  afterText: string
}
```

- `outline` 只包含全文标题，可帮助避免重复一级标题并理解整体结构；
- `headingPath` 表示光标当前位于哪些父级章节之下；
- `beforeText/afterText` 只截取光标附近有限内容，用于判断局部语义和写作风格；
- 不发送完整正文可以控制 Token、延迟和不必要的内容暴露。

标题层级还可以进一步采用“模型输出相对层级、程序计算绝对层级”的方式。模型只判断某个标题是当前章节的同级还是子级，渲染器再结合 `headingPath` 确定使用几个 `#`，从而继续缩小模型的自由度。

### 8.4 校验、修复与降级

合法 Markdown 不代表结果可信，因为普通文本本身也是合法 Markdown。智能粘贴需要结合输入检查：

1. 输出是否为空，是否包含多余开场白或包裹全文的代码围栏；
2. 原文中的 URL、代码、数字和关键条目是否丢失；
3. 输入存在明确列表或标题结构时，输出是否保留这些结构；
4. 标题级别是否符合当前 `headingPath`；
5. 校验失败时最多进行一次带失败原因的修复，仍失败则安全降级。

最坏结果应当是“按普通文本粘贴”，而不是让不可信的 AI 输出删除信息或破坏文档结构。

### 8.5 面试表达：从调 API 到可靠 AI 功能

> 智能粘贴初版直接让模型生成 Markdown，我在测试中发现两个不同问题：一是 LLM 本身存在输出不确定性，二是模型没有当前文档上下文，即使输出合法也可能不适合插入位置。于是我把方案拆成 deterministic-first 和 context-aware 两部分：HTML 结构优先由程序转换，纯文本由模型识别成受限 Block；同时只提供标题大纲、当前标题路径和光标附近文本。模型输出经过渲染、内容保留校验和降级后，仍然只作为 CodeMirror Decoration 候选稿，用户采纳时才写入 Yjs。这个过程让我意识到，AI 工程的重点不是要求模型永远正确，而是限制错误空间，并让错误可检测、可恢复。

### 8.6 智能粘贴原型的最终产品取舍

调研并实现过智能粘贴原型，但发现其边界情况多、触发收益低、容易干扰原生粘贴体验，因此根据复杂度与用户价值评估没有继续上线。

这次取舍不是因为技术链路无法继续实现，而是因为继续投入还需要处理 HTML、纯文本、代码、表格、图片、PDF 断行、标题层级、上下文推导和失败降级，而用户最终感知到的改进可能只是少量 Markdown 标记。该原型保留了剪贴板类型识别、CodeMirror 事件阶段、确定性转换与概率模型边界等技术验证，但不再作为正式产品能力推进。

最终将新增能力调整为“文档保存后的 Markdown 全文质量检查”：触发时机明确，以完整文档为检查对象，输出标题层级、空标题、跳级标题、列表与代码块规范、链接完整性等问题，并区分可由规则确定的问题和需要 AI 判断的表达问题。检查只生成问题清单和修复建议，不直接改写正文。

### 8.7 全文质量检查为什么不用 SSE

润色和翻译使用 SSE，是因为它们会生成一段可能较长的连续文本。流式返回能缩短首字等待时间，用户也可以在生成过程中看到候选稿逐步出现。Markdown 全文质量检查的返回值不同：它不是供用户阅读的连续文章，而是一组必须整体满足约定结构的问题对象，例如：

```ts
interface AIMarkdownQualityIssue {
  severity: 'warning' | 'suggestion'
  category: 'structure' | 'clarity' | 'consistency' | 'duplication'
  line: number
  title: string
  message: string
  suggestion: string
  excerpt: string
}
```

如果对这个结果使用 SSE，会额外引入几个问题：

1. 单个问题对象可能被拆到多个网络分块中，前端仍需维护 buffer 和增量 JSON 解析；
2. 模型尚未输出完时，对象可能缺少字段，无法可靠校验、定位和渲染；
3. 问题列表通常较短，流式展示带来的首屏收益有限；
4. 还需要额外定义“已完成一个 issue”“整个列表完成”“中途失败后保留哪些 issue”等协议语义；
5. 流式追加会让问题数量和排序持续变化，抽屉界面容易抖动。

因此该功能采用普通 HTTP：后端等待模型生成完整 JSON，完成解析和结构校验后，一次性返回问题数组；前端仍使用 `AbortController` 支持取消和新请求覆盖旧请求。这里的原则不是“AI 请求都应该使用 SSE”，而是**根据结果形态选择传输方式**：连续长文本适合流式传输，短小且需要整体校验的结构化数据适合普通 HTTP。

### 8.8 为什么规则检查和 AI 检查不用 `Promise.all`

规则检查与 AI 检查并不是两个地位相同、必须同时成功的任务：

- remark 规则检查运行在本地，速度快、结果稳定，用于标题层级、链接语法等确定性问题；
- AI 检查依赖网络和模型，速度较慢，也可能超时或输出不合法，用于一致性、重复表达和语义歧义等概率性问题。

如果直接使用：

```ts
await Promise.all([
  checkMarkdownRules(markdown),
  checkMarkdownQualityWithAI(markdown),
])
```

那么只有两个任务全部结束后才能展示结果，而且 AI 一旦失败，`Promise.all` 会整体 reject，已经成功得到的本地规则结果也无法进入正常展示流程。这会把可靠能力错误地绑定到不可靠能力上。

当前实现采用两阶段执行：

```text
先运行本地规则
  ↓
立即展示确定性问题
  ↓
再请求 AI 语义检查
  ├─ 成功：把 AI 问题追加到列表
  └─ 失败：提示 AI 检查失败，但保留规则结果
```

这不是单纯追求并发速度，而是在表达产品能力的降级边界：**规则检查是基础能力，AI 是增强能力。** 即使模型服务不可用，用户仍能得到一份有价值的 Markdown 结构报告。若以后性能数据表明两者确实需要并发，也可以同时启动请求，但仍应使用 `Promise.allSettled` 或分别处理结果，不能让 AI 失败吞掉规则结果。

面试时可以概括为：

> 我没有因为项目已有 SSE 就让所有 AI 接口都流式化。润色返回连续长文本，SSE 能改善首字体验；质量检查返回需要整体校验的短结构化 JSON，所以使用普通 HTTP。规则检查和 AI 检查也没有直接 `Promise.all`，因为规则是稳定的基础能力，AI 是可能失败的增强能力。我先展示规则结果，再追加 AI 结果；AI 超时或格式异常时仍保留规则报告，形成可解释的渐进增强和失败降级。

## 9. 当前限制与后续演进

以下是有意识保留的边界，而不是遗漏：

- AI 已实现润色和多语言翻译；智能粘贴完成原型验证后因收益与复杂度不匹配而不再上线，后续新增能力收敛为文档保存后的 Markdown 全文质量检查。
- 不做 RAG 和文档问答，避免在没有明确检索需求时引入向量库、召回质量和权限过滤复杂度。
- SSE 目前具备取消、错误分类和手动重试；后续可补超时、可观测性、指数退避重试与更精细的 HTTP 错误映射。
- 当候选稿期间正文变化时采用“直接失效”策略；未来可探索位置映射，但不能取消最终原文校验。
- 后端当前仍是 Express 模块化结构；NestJS 改造应作为独立阶段，不能和本次前端重构混在同一个提交中。

### 10.1 用 30 秒介绍项目亮点

> 我做的是一个支持多人 Markdown 协作的知识库。协同编辑用 Yjs 和 CodeMirror 处理并发文本合并。AI 部分我没有把它做成普通聊天框，而是做成了选区驱动的写作助手：AI 流式生成的内容只是当前用户本地的候选稿，通过 CodeMirror Decoration 以 diff 形式展示；用户确认后才一次性写入 Yjs 文档，所以不会把未审核的 AI 内容同步给协作者。

### 10.2 为什么 AI 不直接写入协作文档

> 因为流式结果是未审核内容。若每个 token 都写入 Yjs，会把建议同步给所有人，取消还要回滚，并产生大量协同 update。我把候选稿保存在本地 review state，用 Decoration 展示；只有采纳操作才调用带原文校验的 replaceRange，因此共享状态只包含用户确认后的结果。

### 10.3 为什么 AI 用 SSE 而协同编辑用 WebSocket

> 协同编辑是多客户端双向实时同步，需要 WebSocket。AI 生成是一次请求后的服务端单向持续输出，SSE/ReadableStream 更贴合这个模型，协议更轻。我在前端使用 AbortController 取消 fetch，并用 buffer 处理网络分块，避免把半条 SSE 数据当成完整 JSON。

### 10.4 如何处理 AI 生成期间并发编辑

> 发起请求时我会冻结原文、from/to 和候选操作；采纳时重新校验这个范围仍然是原文。文档在生成期间一旦发生本地或远端变更，就清除候选稿，避免覆盖协作者的新内容。当前选择的是保守正确性，后续可以做位置映射优化体验，但最终文本校验不能省。

### 10.5 一个实际踩坑

> 我曾为“防注入”把请求文本的换行替换成空格，导致 Markdown 标题和列表全部变成一行。后来意识到换行是 Markdown 的数据语义，不是可随意清洗的字符。改为只统一 CRLF/LF，并在内联预览使用块级 widget 保留换行。这个问题让我更重视输入清洗的业务语义。

## 12. 代码、状态与 Hook 职责对照

这一节不是要求死记代码，而是要理解：**状态该放在哪里，谁创建、谁消费、谁负责销毁。**

### 12.1 AI 功能的状态归属

| 模块 | 管理的状态/资源 | 不应该管理什么 | 为什么这样拆 |
| --- | --- | --- | --- |
| `useAISelectionHint` | `hint`、延迟计时器、已忽略选区标识、编辑器 DOM 监听 | AI 请求与生成结果 | 它只负责判断“何时值得提示 AI”，不关心用户最后选择什么功能。 |
| `AiInlineHint` | 无本地业务状态，只发出 `action`/`dismiss` 事件 | 选区、请求、编辑器实例 | 纯展示组件更容易替换样式，也不需要测试网络行为。 |
| `AiLanguageMenu` | 无本地业务状态，只返回目标语言 | AI 会话 | 语言是用户输入，菜单不应该知道 SSE 或编辑器。 |
| `useAIReview` | `review`：原文、范围、位置、动作、目标语言 | SSE buffer、CodeMirror Decoration | 它描述的是“一次候选稿会话”，是 AI 业务编排层。 |
| `useAIAction` | `status`、`result`、`error`、私有 `AbortController` | 选区位置、UI 样式 | 它是可复用的流式请求状态机。 |
| `streamAIRequest` | SSE buffer、`ReadableStream` reader | Vue `ref`、组件状态 | 它是协议适配层，便于独立测试与替换请求实现。 |
| `useAIInlineDiff` | CodeMirror `StateField`、临时 Decoration、编辑器扩展是否已安装 | AI HTTP 请求 | 它只做编辑器渲染适配，不能污染业务请求逻辑。 |
| `AiReviewPopover` | 无本地业务状态，只显示采纳/忽略/重试操作 | 候选稿文本的 diff 计算 | 差异已经在编辑器中，操作条只负责发事件。 |
| `EditorPage` | 组合上述能力；采纳时调用编辑器；展示提示信息 | SSE 解析、Decoration 实现细节 | 页面是装配层，不是“万能组件”。 |

### 12.2 `useAISelectionHint`：本地规则先做筛选

它监听 CodeMirror 的鼠标和键盘事件；当选区达到最小长度、经过短暂延迟且没有被用户忽略时，才创建 `AISelectionHint`。

```ts
// 简化后的核心思路
const hint = ref<AISelectionHint>()
let timer: number | undefined

function inspectSelection(view: EditorView) {
  const selection = view.state.selection.main
  const text = view.state.sliceDoc(selection.from, selection.to)

  if (selection.empty || text.trim().length < MIN_SELECTION_LENGTH) {
    hint.value = undefined
    return
  }

  window.clearTimeout(timer)
  timer = window.setTimeout(() => {
    const coords = view.coordsAtPos(selection.from)
    if (!coords) return

    hint.value = {
      text,
      from: selection.from,
      to: selection.to,
      position: { top: coords.top, left: coords.left },
    }
  }, SELECTION_DELAY)
}
```

它没有自动请求模型。这样做是为了避免用户只是复制、拖动或临时选择文本时产生无意义调用；本地规则廉价、可解释，也不把不必要的内容发送给服务端。

### 12.3 `useAIReview`：冻结一次会话，而不是依赖当前选区

用户点击“润色”时，编辑器的选区不能再被当作可靠数据。点击浮层会导致失焦，协作者也可能改变文档；因此先冻结快照：

```ts
async function start(session: AIReviewSession) {
  review.value = session
  await execute(session)
}
```

这里 `review` 是一个 `Ref<AIReviewSession | undefined>`：有值表示候选稿会话存在；设为 `undefined` 表示用户忽略、请求取消或内容变更后失效。

`useAIReview` 不直接 `fetch`，而是委托给 `useAIAction`：

```ts
async function execute(session: AIReviewSession) {
  const feature = AI_FEATURES[session.action]

  await run({
    url: feature.url,
    payload: {
      content: session.inputText,
      ...(session.targetLanguage
        ? { targetLang: session.targetLanguage }
        : {}),
    },
  })
}
```

这让未来新增“精简”“粘贴后结构化”时，只需增加动作配置和入口，不需要复制整套 SSE、取消和错误处理。

### 12.4 `useAIAction`：流式请求状态机

状态类型是：

```ts
type AIActionStatus =
  | 'idle'
  | 'streaming'
  | 'completed'
  | 'cancelled'
  | 'failed'
```

典型状态流转：

```text
idle → streaming → completed
               ├→ failed
               └→ cancelled
```

核心状态和资源：

```ts
const status = ref<AIActionStatus>('idle')
const result = ref('')
const error = ref<AIActionError>()

let activeController: AbortController | undefined
```

注意 `activeController` 故意不是 `ref`：它不是需要驱动 UI 渲染的业务数据，只是取消底层请求的资源句柄。把所有东西都塞进 `ref` 只会增加不必要的响应式依赖。

新请求开始时，先取消旧请求；每个回调都验证 controller 是否仍是当前请求：

```ts
function isCurrentRequest(controller: AbortController) {
  return controller === activeController
}

function handleChunk(controller: AbortController, chunk: AIStreamChunk) {
  if (!isCurrentRequest(controller)) return

  if (chunk.type === 'token') {
    result.value += chunk.text ?? ''
    return
  }

  if (chunk.type === 'done') {
    completed(controller)
    return
  }

  fail(controller, chunk.error ?? defaultServerError)
}
```

这是为了防止旧请求“晚到”：例如先润色 A，马上又翻译 B；即使 A 的网络响应最后才返回，也不能修改 B 的界面状态。

`onScopeDispose(cancel)` 保证页面卸载或使用该 composable 的组件销毁时，浏览器会中止未完成请求。

### 12.5 `streamAIRequest`：为什么需要 buffer

`ReadableStream.read()` 返回的是网络字节块，不是完整 SSE 事件。一个事件可能被拆成多次读取，多个事件也可能被合并在一次读取中。

```ts
buffer += decoder.decode(value, { stream: true })

const events = buffer.split('\n\n')
buffer = events.pop() ?? '' // 保留末尾不完整事件

for (const event of events) {
  const dataLine = event
    .split('\n')
    .find((line) => line.startsWith('data:'))

  if (!dataLine) continue

  const rawData = JSON.parse(dataLine.slice(5).trim())
  onChunk(parseChunk(rawData))
}
```

没有 `buffer` 的实现，在网络抖动时会偶发 `JSON.parse` 失败或丢失 token；这类 bug 很难在本地稳定复现。

### 12.6 `useAIInlineDiff`：编辑器状态不是 Vue 状态

CodeMirror 的 Decoration 属于编辑器扩展状态，而不是 Vue 数据。因此使用 `StateEffect` 下发“设置/清除 diff”的命令，用 `StateField` 保存装饰集合：

```ts
const setInlineDiffEffect = StateEffect.define<InlineDiff | undefined>()

const inlineDiffField = StateField.define<DecorationSet>({
  create: () => Decoration.none,
  update(decorations, transaction) {
    for (const effect of transaction.effects) {
      if (effect.is(setInlineDiffEffect)) {
        return effect.value
          ? createDecorations(effect.value)
          : Decoration.none
      }
    }

    if (transaction.docChanged) return Decoration.none
    return decorations.map(transaction.changes)
  },
  provide: (field) => EditorView.decorations.from(field),
})
```

这段代码有三个层次：

1. Vue 的 `reviewResult` 改变；
2. `EditorPage` 的 `watch` 调用 `renderAIInlineDiff`；
3. CodeMirror 收到 `StateEffect` 后更新 `Decoration`。

Decoration 只改变渲染，不改 `state.doc`，所以不会流入 Yjs。

### 12.7 采纳时为什么必须先清 Decoration

```ts
clearAIInlineDiff()

const replaced = editor.replaceRange(
  currentReview.from,
  currentReview.to,
  currentReview.expectedText,
  reviewResult.value,
)
```

`replaceRange` 会产生真正的 CodeMirror 文档 transaction。若不先清除候选稿，监听器会把这次“用户主动采纳”的真实修改误判为“候选稿期间正文被改动”，然后执行失效逻辑。

`replaceRange` 还会二次校验：

```ts
const currentText = view.state.sliceDoc(from, to)
if (currentText !== expectedText) return false
```

因此即使 Decoration 出现 bug、位置过期或远端内容先变了，也不会覆盖错误文本。

## 13. 面试高频追问与可用回答

以下回答不是逐字背诵模板。面试中先说结论，再说明问题、方案和取舍即可。

### Q1：你的 AI 功能和普通“调用大模型生成文本”有什么区别？

> 我把它设计成协同写作场景下的候选稿系统，而不是把模型输出直接写进编辑器。生成内容只保存在当前用户的本地 review state，通过 CodeMirror Decoration 做差异预览；用户确认后才一次性写入 Yjs。这样避免未审核内容广播给协作者，也避免流式 token 产生大量 CRDT update。

### Q2：为什么不让模型自动调用，而是让用户确认？

> 我把“发现机会”和“执行模型调用”分开。本地规则可以低成本检测长选区或未来的粘贴纯文本，但自动调用会带来成本、隐私和误触发问题。当前采用提示后确认，用户拥有内容控制权；采纳也需要二次确认。

### Q3：为什么不把 AI 结果直接放到 Pinia？

> AI 候选稿只服务于一个编辑页面与其生命周期，不是跨页面共享状态。放 Pinia 会扩大生命周期，还要处理文档切换时清理旧候选稿。它适合放在页面使用的 composable 中；登录用户这类跨页面状态才适合 Pinia。

### Q4：为什么 `AbortController` 不用 ref？

> 它是控制请求取消的资源句柄，不参与模板渲染。`status/result/error` 才是 UI 状态，需要用 ref。保持资源句柄为普通变量可以减少无意义响应式依赖；但页面销毁时仍通过 `onScopeDispose` 释放它。

### Q5：SSE 断连怎么办？

> 当前实现将未收到 done 就结束视为失败，保留已生成部分但不允许直接采纳未完成结果；用户可以点击重试。请求主动取消会归类为 cancelled，不会展示成网络错误。下一步可增加请求超时、错误码分类和带上一次输入的手动重试；不盲目自动续传，因为模型流通常不能从中间 token 精确恢复。

### Q6：为什么 AI 用 SSE，协同编辑用 WebSocket？

> 协同编辑要求客户端之间双向持续同步，所以选 WebSocket。AI 是一次 HTTP 请求后服务端单向连续输出，SSE/ReadableStream 更简单、语义更贴合，也能用 AbortController 取消。按通信模式选协议，而不是整个项目只用一种协议。

### Q7：如果协作者在 AI 生成时修改同一段文字怎么办？

> CodeMirror 收到远端 Yjs update 后会产生 `docChanged` transaction。候选稿监听到任何正文变化会先失效并清除 Decoration。采纳时还会再次验证 from/to 对应文本仍等于请求时原文；不一致就拒绝替换，避免覆盖协作者内容。

### Q8：为什么不直接使用当前 selection 来替换？

> 请求期间选区会因点击操作、失焦或用户移动光标而变化。当前 selection 只代表“此刻光标在哪里”，不是“请求时 AI 处理了哪里”。所以会话开始时冻结 from/to 和 expectedText，采纳时按快照范围替换并校验原文；inputText 则独立表示真正发送给模型的内容，使智能粘贴、续写等“AI 输入不等于编辑器替换目标”的能力也能复用同一套会话。

### Q9：Decoration 为什么不会同步给其他协作者？

> Yjs 绑定的是 CodeMirror 的 document state。Decoration 是 EditorView 的视图扩展状态，只影响本地渲染，不会修改 `state.doc`，因此不会产生 Yjs update。真正执行 `replaceRange` 后才修改 doc 并被同步。

### Q10：Markdown 格式为什么曾经丢失？如何定位？

> 我先判断是传输还是渲染问题：JSON SSE 可以保留 `\n`，但检查服务端发现输入清洗把所有换行替换为空格，模型根本没有收到原始 Markdown。修复为只统一 CRLF/LF、保留换行，同时把候选稿渲染为块级 widget。这个问题说明输入清洗必须尊重领域数据语义。

### Q11：这部分如何测试？

> 纯函数和协议层优先单测：测试 SSE 半包/多事件拼包、错误事件、`normalizeError`、Markdown 换行规范化。composable 测试会 mock `streamAIRequest`，验证取消旧请求后旧 token 不会覆盖新结果。E2E 至少覆盖润色、取消、正文变更失效、采纳与双用户协同修改四条主链路。当前项目尚未补全自动化测试，这是下一阶段的工程化重点。

### Q12：你认为当前方案最大的不足是什么？

> 内容一旦变化就直接让候选稿失效，正确性高但体验偏保守；AI API 地址和认证头仍有进一步抽象空间；SSE 的超时、监控和错误码分类还不完整。我会先补测试与 CI，再优化位置映射和可观测性，而不是继续堆新的 AI 按钮。

## 14. 复盘练习：从代码推导数据流

2. 点击润色到 SSE token 显示成内联候选稿；
3. 用户采纳到 Yjs 向其他协作者同步最终文本；
4. 协作者在生成期间修改正文到候选稿自动失效。

每条链路都按“触发事件 → 谁保存状态 → 谁产生副作用 → 谁清理资源”四个问题讲。
